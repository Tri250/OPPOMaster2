审计总结论

OMaster 当前是「功能可用、迭代活跃」的 1.x 产品，但按正式版（Formal Release）交付标准衡量，尚不具备正式交付资格：签名缺失使 CI 发布产物不可安装、零测试使质量不可回归、31MB 内置资源使交付物超出常规体积、版本文档脱节使发布不可追溯。建议先以 M1 质量基线偿还工程债，再进入 2.0 功能开发。

三、P0 阻断项（正式版门槛，未解决不得发正式版）

P0-1Release APK 无签名配置，CI 产物可能不可安装

app/build.gradle.kts 的 release 构建块没有任何 signingConfig，而 GitHub Actions 的发布链路（beta-release.yml release job）直接把 assembleRelease 产物上传为 Release 附件。未签名的 release APK 无法在设备上安装。已发布的 10 个 Release 中的 APK 是否经过本地签名后上传、或由 CI 直接产出未签名包，仓库内无法证实。需要立即核实线上 APK 的签名状态；若为未签名，则历史 Release 对新用户不可用。

证据：app/build.gradle.kts:33-42（release 块无 signingConfig）；beta-release.yml:183-193（CI 直接上传 APK 附件）。

P0-2CI 无质量门禁：不跑测试、不跑 lint，零测试覆盖

beta-release.yml 仅执行 assembleDebug / assembleRelease，没有 test、lint 步骤。同时测试目录仅有模板文件 ExampleUnitTest.kt（断言 2+2=4）与 ExampleInstrumentedTest.kt。这意味着：任何提交都可能带着编译通过但功能已坏的代码进入 Release，且项目对「回归」完全没有防御能力。此外 build.gradle.kts:29-31 引用的 lint-baseline.xml 在仓库中不存在，lint 基线机制形同虚设。

P0-3版本号、Release、CHANGELOG 三者脱节，发布不可追溯

  • versionName 1.5.1 已提交（2026-05-08）但从未发布，master 领先最新 Release 三个功能提交（订阅自动更新、节日问候系统、相框调色板），用户拿到的 v1.5.0 不含这些功能，而代码自称 1.5.1；
  • CHANGELOG.md 停留在 v1.3.0，v1.4.0 / v1.4.1 / v1.5.0 三个已发布版本没有任何条目（CI 已集成 git-cliff 生成 Release Notes，但仓库 CHANGELOG 未同步，且自动更新 CHANGELOG 的步骤被注释掉）；
  • CHANGELOG 内容与代码相反：v1.0.2 条目写「移除友盟统计 SDK、集成 Firebase Analytics」，而当前代码友盟 SDK 在用（含同意流程）、Firebase 全仓库不存在。文档可信度受损会直接影响开源项目公信力。

P0-4敏感权限组合存在分发合规风险

AndroidManifest 同时声明 READ_PHONE_STATE（友盟 asms 依赖）、SYSTEM_ALERT_WINDOW、REQUEST_INSTALL_PACKAGES、DOWNLOAD_WITHOUT_NOTIFICATION。其中：

  • READ_PHONE_STATE 属于敏感权限，Google Play 审核会要求逐项说明用途；若仅为统计 SDK 服务，应在 2.0 中评估裁剪；
  • REQUEST_INSTALL_PACKAGES（应用内下载 APK 自更新）在 Google Play 属受限行为，若未来上架商店会直接冲突；国内渠道也需在隐私政策中明示；
  • README「隐私说明」仅三行，与实际声明的权限、SDK 清单不匹配，正式版需提供与代码一致的隐私政策与权限用途说明。

四、高优先级问题（P1）

编号问题证据与影响
P1-1APK 内置 31MB 图片，体积治理缺失assets/images 共 31MB（单图最大 jrqx_02.webp 3.4MB）。ABIsplits 只按 ABI 拆 so 库，图片在每个 APK 中完整重复，5 个 APK × 31MB 的分发生成效率与用户下载成本都高。预设样片属「内容」而非「功能」，应外置到云端/社区仓库按需加载，或至少批量压缩。
P1-2上帝类：单文件 1500+ 行FloatingWindowService.kt 1617 行、SettingsScreen.kt 1458 行、MainActivity.kt 852 行、AboutScreen.kt 839 行。悬浮窗是核心卖点却是最大的单点，改动风险集中、无法单测。
P1-3持久层全部 SharedPreferences，复杂对象 JSON 序列化存储8+ 个 Manager 直接读写 SP（Room 已被移除）。订阅列表、自定义预设等结构化数据以 JSON 字符串塞入 SP：无事务性、无迁移版本管理（仅有 ConfigMigration 手工迁移）、大列表读写性能差、崩溃时可能写坏。
P1-4网络层无超时/重试/完整性校验PresetRemoteManager 用裸 Ktor Client：未设置 connect/read timeout，无重试，订阅源内容无哈希/签名校验即写入本地并替换预设库。订阅源被劫持或返回半截 JSON 时（虽有 JSON 解析兜底）缺少最后一道防线。
P1-5双 JSON 栈并存（Gson + kotlinx.serialization）两套解析库同时引入（libs.versions.toml: gson、kotlinx-serialization），存在行为不一致与包体积浪费，2.0 应统一到 kotlinx.serialization。
P1-6社区协作通道堵塞9 个开放 PR（多为 dependabot 依赖升级）无人合并，其中 Gradle/AGP/Compose 升级长期滞留导致依赖债；13 个分支含 9 个 dependabot 分支 + 2 个 revert 分支。缺 Issue/PR 模板与 CONTRIBUTING，协作成本不可控。
P1-7无崩溃上报，线上质量黑盒v1.0.2 决策移除统计又回接友盟，但没有任何 crash 收集策略被明确。正式版必须具备崩溃可观测性（至少友盟 crash 或 Crashlytics 二选一），否则 2.0 大改无法验收。
P1-8minSdk 23 与 README「Android 13+」口径不一致build.gradle.kts minSdk=23（Android 6），README 徽章与「系统要求」写 Android 13+。悬浮窗体验在低版本上无保障，用户预期管理混乱。需二选一：要么提升 minSdk 并下线低版本承诺，要么如实标注。

五、中低优先级与文档问题（P2）

  • i18n 缺口：日语 strings 499 条 vs 中文 676 条（缺约 26%），UI 代码残留 14 处硬编码中文字符串；日语版实际体验不完整。
  • README FAQ 不专业：「悬浮窗无法显示在相机上方」的解决方法写了「换一部新手机 / 旧的放在 XX 回收了」的玩笑话。正式版文档不应出现。
  • 依赖目录冗余：libs.versions.toml 中 material3 声明了两次（androidx-compose-material3 与 androidx-material3 指向同一构件），build.gradle.kts 同时引入，易造成版本漂移。
  • CI 命名误导：workflow 名为 beta-release.yml，但通过手动 dispatch 即产出正式 Release（草稿态），命名与能力不匹配。
  • 工程协作文档缺失：无 CONTRIBUTING.md、SECURITY.md、CODE_OF_CONDUCT.md、Issue/PR 模板（.github 下仅 dependabot.yml 与 1 个 workflow）。
  • versionCode 手工维护：目前 13，无自动化递增，多渠道/多 ABI 并行发布时易出现 versionCode 倒挂。

六、做得好的（2.0 中应保持）

  • 配置中心设计：ConfigCenter 单例 + StateFlow + 迁移机制（ConfigMigration），并有 resetInstance() 测试钩子，是全项目工程质量最好的模块，可作为 2.0 数据层的范本；
  • 隐私合规流程：友盟采用 pre-init → 用户同意后 init → 拒绝则 disable 的标准合规链路，并内嵌隐私政策弹窗与全文页面；
  • 发布工程雏形：git-cliff 自动生成 Release Notes、ABI 拆分产物、tag 校验、草稿 Release 二次确认，思路正确，只差签名与门禁；
  • 内容生态分离：预设内容迁至 OMaster-Community 独立仓库、订阅源机制支持第三方投稿，主仓库与内容仓库解耦，是正确的平台化方向；
  • README 双语 + FAQ + 致谢规范：素材作者逐一署名，社区氛围好（243 stars 对比同类项目不错）；
  • 依赖版本管理：已全面使用 version catalog（libs.versions.toml），dependabot 已启用。

七、2.0 背景与目标

背景（证据链）：

  • 产品已在 5 个月内完成 10 个版本迭代并积累 243 stars，验证了「摄影参数预设库」的需求真实存在；
  • 用户诉求高度集中：3 个开放 Issue（#48 小布记忆导入、#22 root 一键导入、#20 一键导入）全部指向同一能力——跨品牌/跨来源的一键导入预设，这是当前用户最强烈但未被满足的需求；
  • master 上已沉淀未发布功能（订阅自动更新、节日问候、相框调色板），说明功能供给在持续，缺的是发布纪律与质量底座；
  • 审计发现的 P0 工程债（签名、测试、体积、文档脱节）若不在 2.0 一并解决，2.0 的任何新功能都无法以「正式版」标准交付。

2.0 目标（可观测口径）：

  1. 用户可以不依赖手工逐项抄写参数，把外部预设导入 OMaster 并直接使用（覆盖至少一种跨品牌路径）；
  2. 2.0 正式版 APK 体积显著低于 1.x（手段：样片外置/压缩），且安装成功率不因签名问题受阻；
  3. 发布流程具备可追溯性：tag ↔ versionCode ↔ versionName ↔ Release ↔ CHANGELOG 五者一致；
  4. 核心逻辑（预设解析、配置读写、订阅更新）具备自动化回归测试，CI 在测试或 lint 失败时阻断发布。

八、2.0 定位与主题

2.0 主题：「从参数库到预设生态平台」+「正式版质量基线」

1.x 解决的是「参数在哪看」；2.0 解决「参数怎么进来、怎么保持最新、进来的是否可信」。一键导入是入口，订阅体系是管道，质量基线是地基。三者共同构成 2.0 的「生态化」叙事，同时把 v1.5.1 以来的存量功能正式发布给用户。

10.2 重点模块升级卡片

模块卡 A ｜ 悬浮窗（P1 · 体验增强 + 架构拆分）

现状（证据）：三种窗口形态（展开 / 收起 / 紧凑）+ 左右切换 + 透明度 30–70 可调 + 动态参数提取 + Realme 品牌特判（isRealmePreset、extract11Params）+ 悬浮球引导；实现为传统 View 体系（LinearLayout / TextView / 递归 findViewWithTag），与主 App 的 Compose 双轨并存。

1.x 遗留问题：1617 行单类同时承载窗口生命周期、视图构建、参数解析三个职责；视觉与交互规则在 View / Compose 两处维护；品牌差异以硬编码写死在核心类，每支持一个新品牌都要改核心逻辑。

2.0 升级动作：

  1. 职责三分：WindowController（生命周期与权限）+ PresetParamMapper（预设 → 展示模型）+ WindowRenderer（渲染），PresetParamMapper 可单测（归入 FR-02c 测试基线）；
  2. 品牌特判数据化：窗口布局差异改为预设 JSON 元数据声明（如 layout 字段），新增品牌不再改代码；
  3. 体验增强：跟拍场景「一键置顶 + 防误触锁定」，紧凑模式支持参数轮播；
  4. 与导入体系打通：悬浮窗可直接切换到「我的导入」自定义预设（FR-01），形成「导入 → 跟拍」闭环。

依赖：R-1 预设状态机、FR-04 订阅数据、ConfigCenter 既有的透明度/模式配置。

模块卡 B ｜ 预设导入与创建（P0 · FR-01 的模块落点）

现状（证据）：UniversalCreatePresetScreen 支持从零创建与编辑自定义预设；无文件 / 剪贴板 / 分享任何导入路径——这正是 Issue #48、#22、#20 三个开放诉求的空缺。

十一、功能需求（核心）

FR-01 P0 一键导入体系

目的：让用户把外部渠道获得的预设（他人分享的截图/口令/文件/其他 App 的参数）在数秒内转为 OMaster 可用预设，替代逐项手抄。直接响应 Issue #48、#22、#20。

子项能力触发与行为
FR-01a通用文件导入用户在首页「+」选择「导入预设」→ 系统文件选择器（限定 .json / .omaster 后缀）→ 解析校验（字段完整性按订阅源同一规则，见 R-3）→ 成功后进入预设详情并可保存为自定义预设。同文件重复导入时提示「已存在同名预设」，提供覆盖/另存选项。
FR-01b剪贴板/口令导入检测剪贴板中符合预设 JSON 结构的文本 → 首页顶部出现「检测到可导入预设」胶囊 → 点击进入预览确认页 → 确认后入库。剪贴板读取遵循 Android 13+ 系统提示，不做后台静默读取。
FR-01c分享接入导入注册 ACTION_SEND text/plain 与 .json 文件的分享入口：用户在其他 App（微信/QQ/网盘）分享 JSON 到 OMaster 即进入导入预览。Manifest 已有 QQ/TIM 包可见性声明，可顺带识别来源。
FR-01d厂商参数截图辅助录入无法结构化导入时，提供「对照录入」视图：左侧显示用户选择的参数截图，右侧表单逐项填写并实时预览，降低手抄成本。[假设，待定：OCR 自动识别参数不在 2.0 承诺范围内，作为 2.1 候选]
FR-01eRoot/自动化路径导入（高级）针对 Issue #22 的进阶方案：提供「通过无障碍/Root 提取当前相机参数」的实验性开关，默认关闭并在开启时二次确认风险。[假设，待定：无 Root 设备依赖厂商内容提供器，可用性因机型而异，需在 M2 期间实测主流机型后决定是否保留]

结果与状态：导入成功 → 生成自定义预设（走既有 CustomPresetManager 存储）→ 可收藏/编辑/悬浮窗使用；导入失败 → 明确报错原因（格式错误/缺少必填字段/版本不兼容），不产生半成品数据。权限：仅文件导入需存储读取权限（遵循分区存储，SAF 选择器免权限）。

FR-02 P0 发布工程基线

目的：使 CI 产出的 Release 具备「可安装、可回归、可追溯」三项正式版底线能力。

子项能力与规则
FR-02a签名：建立 keystore 管理方案，release 构建强制签名（GitHub Secrets 注入或维护者本地签名后上传，二选一，见开放问题 Q1）。CI 产物文件名与 Release 附件统一命名（如 OMaster-vX.Y.Z-arm64-v8a.apk）。未签名构建在 CI 中直接失败。
FR-02b质量门禁：CI 在 assemble 前执行 testDebugUnitTest 与 lint（补齐 lint-baseline.xml 或移除引用），任一失败阻断 merge 与发布。
FR-02c核心逻辑测试基线：为预设 JSON 解析/校验、ConfigCenter 读写与迁移、订阅更新判定（build 号比较）三类纯逻辑补齐单元测试，作为 2.0 的最低回归保障；UI 自动化测试不在 2.0 范围。
FR-02d版本自动化：versionCode 由 CI 依据 run number 或 tag 自动生成；发布 workflow 改名 release.yml 并增加 tag 触发（推送 vX.Y.Z 即自动走构建→门禁→草稿 Release 流程），手动 dispatch 仅作兜底。

FR-04 P1 订阅中心升级

目的：把「订阅源」从隐藏配置升级为 2.0 生态入口，同时将 master 未发布的订阅自动更新能力正式化。

子项行为与规则
FR-04a订阅目录页：内置官方源（OPPOMaster 社区源）+ 用户自建源列表；每条显示名称、作者、预设数、build 号、上次更新时间；支持添加/编辑 URL/启停/删除（沿用 ConfigCenter 既有操作）。空态页引导去社区仓库投稿。
FR-04b自动更新正式化：沿用 master 已实现的每日一次自动更新判定（shouldAutoUpdateSubscriptions），增加更新失败重试（当日下次启动重试）与失败静默降级——自动更新失败不打扰用户，仅订阅页显示「上次同步失败」。
FR-04c内容可信：订阅 JSON 增加 minAppVersion 兼容字段与可选 sha256 完整性字段；Ktor 客户端统一配置连接/读取超时；解析失败的订阅源绝不覆盖本地已缓存版本（保留上一次可用数据，即「最后已知良好」策略）。

FR-05 P1 体积治理

  • 预设样片图从 APK assets 迁出为「首次进入详情时按需下载 + 本地缓存」（复用 ImageCacheManager），或至少全量重压缩（目标单图 ≤ 500KB、总量目标见 NFR-1）；
  • 下载源跟随订阅源仓库（社区仓库已独立维护，天然承载样片）；无网时显示占位卡片而非阻断参数查看——参数文本永远本地可用，图片是增强；
  • 统一 JSON 栈至 kotlinx.serialization，移除 Gson；合并重复的 material3 依赖声明。

FR-06 P1 国际化补全

  • 日语 strings 补齐至与中文对齐（当前缺口约 26%）；清理 UI 代码中 14 处硬编码中文，全部迁移至 strings 资源；
  • 建立 CI 检查：三语 strings 数量差超过阈值（建议 5%）时 CI 告警；
  • 预设内容 i18n 沿用 PresetI18n 机制并在社区仓库文档中向投稿者说明。

FR-07 P1 崩溃可观测与隐私透明

  • 接入崩溃收集（友盟 crash 模块或 Crashlytics 二选一，见开放问题 Q4），崩溃上报同样受「用户同意统计」总开关约束，拒绝时完全静默；
  • 重写隐私说明页：与 Manifest 权限、SDK 清单一一对应（当前 README 三行说明不满足正式版要求）；评估移除 READ_PHONE_STATE 的可行性（若友盟 asms 可降级配置则移除）；
  • 应用内自更新（REQUEST_INSTALL_PACKAGES）在隐私政策中明示用途；若未来上架应用商店，提供商店版构建变体（关闭自更新，见 Q3）。

十二、共享规则与异常

规则定义（全文唯一出处）
R-1 预设状态机预设仅有四态：内置（随 APK/内置 JSON，不可删除）、订阅（来自订阅源，随源更新，不可单删，可随源停用）、自定义（用户创建/导入，可编辑可删除，删除需二次确认）、收藏（任何状态的预设都可收藏，收藏关系存于 FavoriteManager）。新预设标记（NEW）只对内置与订阅预设生效。
R-2 版本判定订阅源更新以 build 整数递增为准；App 兼容性以订阅 JSON 的 minAppVersion 与本机 versionName 比较，低于要求时显示「源需要更新 App」而非静默失败。
R-3 导入/订阅共用的校验规则JSON 解析失败、缺 name/author 必填字段、预设数 > 上限（暂定 500，防恶意超大文件）三者任一命中即拒绝，错误信息向用户明示原因。校验规则在 FR-01a 与 FR-04 中复用同一实现。
R-4 数据安全底线任何远程内容（订阅、样片、更新包）在写入/执行前完成校验（R-3 / sha256 / 签名）；本地数据写坏时（JSON 解析失败）回退到内置 presets.json，永不出现白屏空预设库。
R-5 统计与隐私开关isAnalyticsEnabled 是统计与崩溃上报的唯一总开关（默认值取 ConfigCenter 现状）；关闭时初始化即 disable，重新开启即时生效。

关键异常路径：导入失败（原因明示，见 R-3）｜订阅源不可达（保留上次数据 + 标记失败，见 FR-04c）｜悬浮窗权限被系统限制（沿用现有引导弹窗 + 品牌已知问题文档）｜更新包下载失败（保留 REQUEST_INSTALL_PACKAGES 流程的失败重试入口）。
