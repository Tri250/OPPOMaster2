OMaster 2.0 正式版交付升级方案

本方案是 OMaster 从 v1.5.x 升级至 v2.0 正式版的完整交付执行方案：版本策略、功能交付、工程交付、质量保障、里程碑与验收标准，一次讲清，按出口标准验收。

编制依据：《OMaster 正式版交付审计 & 2.0 升级规划》（2026-10-13，审计快照 master@8873942）｜ 方案状态：待维护者评审

一、方案概述

OMaster v1.5.x 功能闭环完整、迭代活跃（5 个月 10 个版本、243 stars），但按正式版交付标准衡量存在 4 项 P0 阻断（发布产物签名缺失、零测试无门禁、版本三方脱节、敏感权限合规）与多项 P1 工程债。本方案以 「不做商业化」为既定前提，分三个里程碑完成质量基线偿还与生态能力建设，交付一个可安装、可回归、可追溯、合规透明的 v2.0 正式版。

  • 交付主线：M1 质量基线（发布 v1.5.1 清存量）→ M2 生态能力（一键导入 + 订阅中心，v2.0-beta）→ M3 正式发布（v2.0）；
  • 文档配套：审计证据链见《OMaster 正式版交付审计 & 2.0 升级规划》，本方案不重复论证，直接给执行动作与验收标准；
  • 验收原则：所有里程碑不设日期，以第十章「正式版验收清单」的出口标准（DoD）逐项验收。

四、明确约束与边界（不做商业化）

本方案既定约束：2.0 不做任何商业化

以下条款为方案级约束，所有功能与工程决策不得与之冲突：

  • 无付费与广告：不引入付费墙、订阅付费、广告位、开屏推广、应用内购买；「订阅」一词仅指免费的预设源订阅（RSS 式内容分发），不涉及支付；
  • 无数据变现：统计 SDK（友盟）仅用于质量与用量分析，受 isAnalyticsEnabled 总开关约束（默认遵循现状），不采集用于推荐/广告画像的数据，不与第三方共享变现；
  • 内容生态非商业：预设源与样片由 OMaster-Community 社区仓库免费分发，投稿者署名致谢（沿用现有 README 致谢机制）；
  • 协议保持：仓库继续以 CC BY-NC-SA 4.0 分发（BY 署名 / NC 非商业 / SA 相同方式共享），与应用内不做商业化的约束一致；
  • 范围边界：平台仅 Android；不做 iOS、不做云端账号体系、不做 AI 参数推荐（2.1+ 另议）。

五、版本与发布策略

5.1 版本号规范

  • versionName：主.次.修订（semver 口径）；正式版如 2.0.0，测试版 2.0.0-beta1；
  • versionCode：由 CI 依据构建流水号自动生成，禁止手填，杜绝多渠道倒挂；
  • Tag：vX.Y.Z（如 v2.0.0），beta 加后缀 v2.0.0-beta1；
  • 五者一致性（tag / versionCode / versionName / Release / CHANGELOG）由 CI 校验，不匹配即失败（G-3）。

5.2 发布通道

通道内容用途
GitHub Release（prerelease）beta 全量 APK（5 ABI）公测收集反馈，Issue 反馈模板驱动
GitHub Release（正式）正式版全量 APK + git-cliff 生成的更新说明主分发渠道
蒲公英 / 蓝奏云镜像与 GitHub 正式版同包同步国内可达性（沿用现有镜像体系，README 口径不变）

5.3 发布流程

推送 tag→ CI 门禁（测试 + lint + 版本校验）→ assembleRelease + 签名→ 草稿 Release（附 APK + Release Notes）→ 维护者真机验收→ 发布 + 同步 CHANGELOG / 镜像

任一门禁失败流程终止；草稿 Release 为人工复核点（沿用现有 softprops/action-gh-release 草稿机制）。手工 dispatch 仅作兜底入口。

5.4 回滚与数据安全

  • 版本回退：Release 页保留历史版本 APK 可随时下载；自更新检查不删除旧版本产物；
  • 数据兼容：遵循审计报告 R-4 底线——订阅 / 导入内容写入前完成校验，本地数据损坏时回退内置 presets.json，任何升级路径不允许出现「升级后预设库丢失」；自定义预设与收藏的存储结构变更必须带迁移（沿用 ConfigMigration 机制）；
  • beta 缓冲：破坏性存储变更必须在 beta 期完成迁移验证，才允许进入正式版。

六、功能交付方案（FD）

FD = Feature Deliverable。每项含交付内容、验收标准、依赖。优先级沿用审计报告 P0/P1/P2 口径；模块级证据见审计报告第十章模块卡 A–F。

FD-01 P0 一键导入体系（2.0 旗舰功能）

交付内容：在「导入与创建」模块新增四条标准路径 + 一条实验路径：

路径交付内容验收标准
FD-01a文件导入：SAF 选择 .json / .omaster，解析校验后入库合法文件 3 步内完成导入；重复导入出现「已存在同名预设」，提供覆盖 / 另存；非法文件给出具体原因（R-3）
FD-01b剪贴板口令导入：检测可导入文本 → 顶部胶囊 → 预览确认遵循系统剪贴板读取提示，无后台静默读取；确认前不写入任何数据
FD-01c分享接入：ACTION_SEND 接收 text / json 分享从微信 / QQ / 网盘分享 JSON 可直达导入预览页
FD-01d对照录入：左截图右表单，复用现有创建表单录入过程随时保存草稿；完成后与手动创建预设行为一致（R-1）
FD-01eRoot / 自动化提取（实验开关，默认关闭，二次确认）[假设，待定：以 M2 主流机型实测可用率决定保留或移出 2.0]

依赖：R-1 预设状态机、R-3 校验规则（与订阅共用）、CustomPresetManager 存储通道。里程碑：M2（a–c 全量，d 随行，e 实验）。

FD-02 P0 订阅中心升级

交付内容：①订阅目录页（官方源 + 自建源列表：名称 / 作者 / 预设数 / build / 上次更新时间，空态引导投稿）；②自动更新正式化（沿用 master 已实现的每日判定，失败静默降级 + 订阅页标记「上次同步失败」，绝不覆盖本地可用数据）；③内容可信（minAppVersion 兼容字段、可选 sha256、R-3 校验、Ktor 统一超时重试）。

验收标准：断网 / 半截 JSON / 超构建号的源三种异常下，本地预设库均完整可用并展示明确状态；自动更新失败不影响任何已缓存内容。依赖：PresetRemoteManager 网络改造。里程碑：M2。

FD-03 P1 悬浮窗重构与体验增强

交付内容：①1617 行 FloatingWindowService 拆分为 WindowController（生命周期）/ PresetParamMapper（预设→展示模型）/ WindowRenderer（渲染）；②品牌特判（Realme 等）数据化为预设 JSON 元数据 layout 声明；③体验增强：一键置顶、防误触锁定、紧凑模式参数轮播；④可直接切换「我的导入」自定义预设，形成「导入 → 跟拍」闭环。

验收标准：PresetParamMapper 单测全绿（归入 ED-03）；三窗口形态在回归清单中行为与 1.x 一致；新增品牌布局不再需要修改核心类。里程碑：M2 启动拆分，M3 收尾（拆分与增强不互相阻塞）。

FD-04 P1 相框出片正式化与打卡联动

交付内容：①相框调色板等 master 存量功能随 M1 v1.5.1 / M3 v2.0 正式发布给存量用户；②明确导出分辨率与水印策略 [假设，待定：默认策略发布，beta 期收集反馈]；③相框作品一键生成本日打卡，打通「拍 → 框 → 打卡」闭环。

验收标准：存量用户升级后相框功能可用无回归；打卡联动路径端到端可走通。里程碑：M1 / M3。

FD-05 P2 发现页收编

交付内容：「敬请期待」占位卡（ComingSoonCard）要么兑现要么移除，正式版不保留空承诺；打卡与相框联动（见 FD-04）。边界：2.0 不在打卡 / 扫街模块新增大功能。验收标准：发现页无占位卡。里程碑：M3。

FD-06 P1 设置重构与新设置项

交付内容：SettingsScreen（1458 行）拆分为「设置骨架 + 独立区块组件」；更新设置区独立为 UpdateSettingsSection；为 2.0 新增设置项预留挂载位：导入行为、订阅自动更新、隐私开关（总开关 R-5 既有）、实验功能开关。

验收标准：拆分后所有设置项读写行为与 1.x 一致（ConfigCenter 流不变）；新增设置项均可在对应区块找到。里程碑：M2–M3。

FD-07 P1 国际化补全

交付内容：日语 strings 由 499 条补齐至与中文（676 条）对齐；清理 UI 代码 14 处硬编码中文；CI 增加三语数量差校验（阈值 5%，超差告警）。验收标准：日语界面无回退中文的关键路径；CI 告警生效。里程碑：M3。

七、工程交付方案（ED）

ED = Engineering Deliverable。工程项是正式版的门槛条件，与功能项同等验收。

ED-01 P0 签名体系

  • 建立 release 签名配置（signingConfig），密钥注入方式建议 GitHub Secrets（keystore + 密码 base64 注入） TBD Q1：若维护者不接受云端托管，则降级为「维护者本地签名后上传，CI 产 unsigned 包仅作内部验证」并在流程中显式标注；
  • 核实历史 Release（v1.0.0–v1.5.0）线上 APK 的签名状态；若为未签名包，在 v1.5.1 Release 说明中向用户说明并引导换装；
  • CI 中 release 构建未配置签名即失败；产物统一命名 OMaster-vX.Y.Z-{abi}.apk。

ED-02 P0 CI 质量门禁

  • 构建前强制执行 testDebugUnitTest + lint，任一失败阻断 merge 与发布；
  • 补齐缺失的 lint-baseline.xml（当前 build.gradle.kts 引用了一个不存在的文件），或移除该引用并保持 lint 零报错；
  • 版本一致性校验（G-3）以脚本实现并纳入 workflow；
  • workflow 改名 release.yml，tag 推送触发自动发布，手动 dispatch 兜底；
  • 启用被注释的 git-cliff CHANGELOG 自动提交步骤。

ED-03 P0 测试基线（三类单测）

  • 预设解析与校验：合法 / 缺字段 / 超上限 / 非法 JSON（R-3 全分支）；
  • ConfigCenter：读写、默认值、dark_mode_v2 迁移、resetInstance() 隔离；
  • 订阅更新判定：build 号比较、每日判定、失败保留「最后已知良好」；
  • 延伸：悬浮窗 PresetParamMapper（随 FD-03 落地）。UI 自动化不在 2.0 范围。

ED-04 P1 体积治理

  • 预设样片（assets/images 31MB，单图最大 3.4MB）迁出 APK：托管于 OMaster-Community 仓库，详情页按需下载 + ImageCacheManager 本地缓存；
  • 降级原则：无网 / 下载失败时显示占位卡片，参数文本永远本地可用，图片只是增强（R-4）；
  • 过渡兜底：若外置方案受阻，最低限度全量重压缩（单图 ≤ 500KB）并复核 NFR 目标；
  • 统一 JSON 栈至 kotlinx.serialization，移除 Gson；合并 toml 中重复的 material3 声明。

ED-05 P0 合规透明

  • 重写隐私说明：与 Manifest 权限、SDK 清单一一对应（现 README 仅三行，不满足正式版要求）；
  • 评估移除 READ_PHONE_STATE（友盟 asms 可降级配置则移除，保留则在隐私政策中逐项说明用途）；
  • 应用内自更新（REQUEST_INSTALL_PACKAGES）在隐私政策明示；预留「商店版」构建变体开关（关闭自更新），当前不启用上架 TBD Q3；
  • README FAQ 移除玩笑式表述，改为品牌已知问题列表；统一 minSdk 口径（[假设，待定] 建议 minSdk 保持 23 + README 明示「悬浮窗完整体验建议 Android 13+」）。

ED-06 P1 崩溃可观测

  • 接入崩溃收集，选型二选一：友盟 crash（复用现有 SDK，增量小）或 Crashlytics（README 曾失实宣称，需正式引入） TBD Q4；
  • 崩溃上报与统计共用 isAnalyticsEnabled 总开关（R-5），拒绝即完全静默——与「不做商业化」约束一致，崩溃数据仅用于质量修复。

ED-07 P1 版本与文档一致性 + 社区协作通道

  • M1 发布 v1.5.1 清空存量（订阅自动更新、节日问候、相框调色板）；CHANGELOG 补齐 v1.4.0 / v1.4.1 / v1.5.0 / v1.5.1，修正 v1.0.2「移除友盟 / 集成 Firebase」的失实记载；
  • 补充 CONTRIBUTING.md（预设走社区仓库的指引已有基础）、SECURITY.md、Issue / PR 模板（导入问题反馈模板随 M2 上线）；
  • 9 个滞留 PR（多为 dependabot）批量验证后合并或关闭，13 个分支瘦身。

层级内容执行时机
